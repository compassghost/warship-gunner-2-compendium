# Habakkuk (EUR-J-483 "Sizzling Iceberg") - what the executable says

Source: `iso_extract/SLUS_213.87` (same setup as `notes/hell_atsche.md`: file offset 0x1000 = address 0x100000, Capstone MIPS64 little-endian, one word at a time).
Static reading only; nothing was run. **Confirmed** = read directly from the code; **inferred** = my interpretation of field use.

## It has no mission hook of its own
- EUR-J-483 is row 48 of the per-mission hook table at 0x29af30 and points at the default hook 0x1e7050 (Hell Atsche, row 66, has its own). So the mission only places the boss; the behaviour lives in the boss's **entity-class code**.
- Entity class **605 = 0x25d Habakkuk** (DAT entry 3 array 3, resource 277 = CHR 1176 `BOS07`). Class **1070 = 0x42e** has no name in the table; its resource 294 is **CHR 1177 = `BOS07A`**, the ten iceberg meshes, so 0x42e is the **ice**. (Confirmed.)
- Code that mentions class 605: four places - damage application (0x15510c), two class dispatch trees (0x16e76c, 0x1830d8; not read yet) and a small damage helper (0x1886f4). The Habakkuk update / init handler is the function at **0x188720** (reached from the dispatch; it is the only code that spawns class 0x42e).

## Init (first call, 0x188a60-0x188bdc) - confirmed
- Zeroes the state fields at +0x9c..+0xc0 and sets two pools to **100000 (0x186a0)**: `+0xa8` and `+0xb4`; `+0xac` = `+0x34 / 20` (a twentieth of the boss's own value at +0x34); timers `+0xf8` = 60, `+0xfa` = 30.
- **Difficulty tiers** (byte at 0x2b281b, same global the rest of the game reads): below 2 -> `+0xf8`/`+0xfa` = 20 / 10; exactly 2 -> 30 / 15; above 2 -> 60 / 30. (Which in-game difficulty each value is was not checked.)
- Creates **ten entities of class 0x42e** (the ice) in a loop, stores their pointers at `+0xc4..+0xe8`, gives each `+0x34 = +0x38 = 100000`, marks them with flags 0x101 / 0x3000, then registers them. Ten matches the ten ice meshes of BOS07A in the viewer.

## Damage routing (0x15510c and 0x1886e8) - confirmed
- When the boss or an ice piece (class 0x25d or 0x42e) is hit, the code looks at a byte in the weapon / shot record (`[shot+7]`). For the values **0x5c (92), 0x7a (122), 0x93 and 0x94 (147, 148)** the damage is not added to the normal damage counter (`+0x30`) but to a second counter at **`+0x98`**, multiplied by **4** for the carrier and **8** for an ice piece (0x1886e8). All other weapons use the normal counter.
- **RESOLVED (fourth pass): the four special weapons are the FIRE weapons.** Ids 92 / 122 / 147 / 148 are rows of the *program's* weapon table (DAT entry 7, rows on the natural 144-byte grid with the weapon-type id at +7; **not** chip item ids). Calibrating that table against the guide's own numbers fixes its layout: `+0x22` weight, `+0x40` damage (u16), `+0x70` reload, `+0x72` dispersion, `+0x74` range (u16). Row 417 (id 92): reload 64, dispersion 256, range 2000, weight 20, damage 45 = **Napalm Grenade Gun** (ROCKET 4). Row 469 (id 122): 650 / 64 / 4000 / 150 / 2000 = **Napalm Missile** (MISSILE 41). Row 530 (id 147): 200 / 256 / 500 / 120 / 4 = **Flamethrower** (ROCKET 10). Row 531 (id 148): 200 / 256 / 700 / 100 / 8 = **New Flamethrower** (ROCKET 12). Every field matches the guide, so the identification is solid. It also fits the user's observation in the game (2026-11-15): the flamethrower removes the ice but does little to the ship - the ice is destroyed for good by the tally mechanism above, while the flamethrowers' own damage per hit (4 and 8) is tiny. The same three ids 92 / 147 / 148 are special-cased in the hit roll at 0x154ec0 as well (fire weapons treated differently when they hit). The earlier "oxygen torpedo / VLS / ASROC" reading came from matching ids to the wrong table and is wrong.
- **RETRACTED (third pass, superseded by the bullet above) - the weapon names below are wrong.** The user pointed out that ASROC is submarine-only (guide attack flags `--U-u`) and cannot target an iceberg. Re-checking: DAT entry 7 holds several 144-byte-row tables. The one I matched to the chips (byte 0 = item id, rows 1-265) is **not** the one the program reads at `+7`. The program's table is a different, patchy one: on the file's own 144-byte grid the id sits at +7 in ascending segments (rows 354-376, 389-429, 527-540, 751-766, ...). In it the four ids are **row 417 (id 92, code 1500)**, **row 469 (id 122, code 1435)**, **row 530 (id 147, code 1801)** and **row 531 (id 148, code 1802)**; the 16-bit code at +0 counts up inside families (1500-1512, 1600-1610, 1800-1811, ...). Its numbers do not match the guide's damage / reload / rounds / range for the chips of the same position, so its ids are not chip item ids, and which weapons rows 92 / 122 / 147 / 148 are is **unknown**. Everything in the next bullet that names weapons, and the "validation pass" below it, should be read with that in mind (the table / chip-ordering evidence belongs to the other table). What remains solid is the code: four ids are singled out, and they feed the permanent-damage tally described above.
- **Which weapons (second pass, superseded):** the byte at `[shot+7]` is the weapon's **global item id** (the same numbering as `item_id` in `data/tree_raw.json`; weapon records are 0x90 bytes with the id at +7, table base pointer at 0x2ae700, filled at run time). Evidence: the torpedo code at 0x1793a4 is a switch on ids **0x55-0x5b (85-91)**, which are the guided "Gdd" torpedoes and the Anti-Mine Torpedo, each setting its own flag; the missile / rocket handler table at 0x28df88 is keyed by ids 125-163 (the VLS missiles, ASROC, cruise missile, rockets); other tests in the program compare against ids that are gun, torpedo and missile chips (e.g. 128 = Anti-Air Missile I). Not proven by running the game, but every comparison I could name fits.
  So the four special weapons are:
  - **92 = 45.0cm Oxy Trp** (the first oxygen torpedo; hidden chip, TORPEDO 48)
  - **122 = Anti-Ship Missile VLS I** (hidden chip, MISSILE 7)
  - **147 = ASROC I** (hidden chip, MISSILE 32)
  - **148 = ASROC II** (MISSILE 33)
  **Validation pass (what holds and what does not):**
  - *Holds:* DAT entry 7 is a table of 144-byte weapon rows, 265 of them in item-id order (byte 0 of row n on the natural grid = n; with the id read at +7 the program's way, the grid is 7 bytes earlier). Per chip group the class byte is constant and the tier byte rises like the chips (torpedoes 12-15, explosives 16-17, missiles 17-21, rockets 18-19, flares 20), so row n really is item n. Chip item ids above 255 wrap (flamethrower 905 -> 137, New Flamethrower 907 -> 139, Napalm Missile is 161).
  - *Holds:* the same three ids 92, 147, 148 are special-cased a second time in the same damage routine (0x154ec0, the hit / evasion roll), so they are a deliberate group in the code, not a misread of one comparison. 122 appears only in the Habakkuk branch (and in an effect picker at 0x155588 together with ids 91, 121, 67, 113, 155).
  - *Does not hold / unknown:* I never found the code that fills the weapon-table pointer (0x2ae700), so I cannot prove the table the damage routine reads is this DAT 7 block at that alignment. The 16-bit words at +0x86 / +0x88 in that alignment look like counters (0x2a43, 0x2b44, ...), not the flag words the code tests (0x10, 0x20, 0x1000), which is a warning sign. Nothing here was run.
  - *Fire:* no weapon row carries the 0x10 / 0x20 / 0x1000 bits the damage routine tests; the flamethrower (137, 139) and napalm (161) ids are compared nowhere in the Habakkuk code or the damage routine. So by this reading flames are ordinary damage (the ice shrinks and regrows) - the code gives no fire weakness. A fire effect could still exist in code I did not find.
  - One idea that fits (unproven): 92 (oxygen torpedo), 147 / 148 (ASROC, a rocket-launched torpedo) are underwater attacks and most of an iceberg is below the waterline; 122 (Anti-Ship Missile VLS I) does not fit that.
  They are the lowest-tier chip of their family: the 48.3 cm and larger Oxy torpedoes (ids 93+), Anti-Ship Missile VLS II / III and ASROC III are **not** in the list as far as the code goes. The barrel-count chips (3, 4, 5 barrels) have different item ids (9, 12, 76), so whether a multi-barrel launcher of the 45 cm Oxy torpedo counts is not known (the shot most likely still carries the torpedo's id). The routine at 0x1886e8 has this one caller, so these four are the only way into the extra counter.

## Per-frame update (0x188780-0x188e98) - mostly confirmed
- **Permanent loss**: while the ice is up (`+0x9f` = 0), damage counted in `+0x98` adds `+0x98 * 100` to **`+0xb0`**, capped at `+0xb4`. `+0xb0` is then taken off the ceiling of the ice pool, so this damage cannot be regrown (inferred meaning: a "scar").
- **Damage pool**: ordinary damage (`+0x30`) is taken off a pool chosen by `+0x9f` / `+0x98` (pool 0 = `+0xa8`, pool 1 = `+0xac`), floored at 0, and the counters are cleared.
- **Regeneration**: while the carrier has not changed phase (`+0x9e` = 0) the ice pool `+0xa8` is **refilled every frame** by roughly `+0xf8 * +0xac / 1920` (the numerator scales with the difficulty tier above), and never above `(+0xb4 - +0xb0)`. The ratio `+0xa8 / +0xb4` is fed to 0x188ea8 (the ice's visual size / state), and `+0x9f` is set to 1 when that ratio is at or below a constant at 0x2b126c, 0 above it. (Confirmed code; the "ice size" reading of 0x188ea8 is inferred.)
- **Ten ice pieces**: each frame the loop at 0x188db0 updates all ten (`0x182e60` with slot 0x1a + n, then `0x188f30`); a piece whose update returns 0 is dropped (`+0xc4 + 4n` cleared).
- **One ice piece (0x188f30, read in the second pass - confirmed code)**: every piece has `+0x34` hit points, `+0x38` maximum (100000), `+0x30` damage this frame, `+0x98` the special counter and `+0x9c` a permanent-damage tally. Each frame: if `+0x98` is not 0, `+0x9c += +0x98 * 100` and `+0x98` is cleared; **if the tally reaches the maximum the piece is freed (destroyed for good)**. Ordinary damage (`+0x30 * 100`) is taken off `+0x34` (floored at 0). Then the piece **regrows** by `(regrowth value from the boss, +0xf8) * (frame delta) / 1920` per frame, never above `maximum - tally`, and `+0x34 / +0x38` sets its size (0x11b350). So ordinary fire only makes the ice shrink temporarily, while hits from the four special weapons (x8 on a piece) build the tally that removes pieces permanently.
- **Phase change** (0x188820-0x1888cc): when the pool in `+0xac` is gone and `+0x9e` = 0, it plays sound 0x54, sets `+0x9e` = 1, sets a timer `+0xa0` = **0x780 = 1920** ticks, shrinks three size fields of the shared record and sets flag 0x100. From then on the regeneration block is skipped. When the timer runs out the handler calls state changes 2, 3 and 0x18 (0x182d28). A second timer `+0xa4` (0x7080 = 28800) is started with sound 0x5c in the branch at 0x188e50-0x188e94.
- Clean-up (flag 0x80 on the entity): frees all ten ice entities (0x106628) and the shared record.

## What removing the ice does (fifth pass, from the user's question 2026-11-15)
- `0x182fb8` (read this pass) returns the **state code of the model's current pose**: it looks up `[self+0x3c]` (current animation index) in the model's state table and returns a 16-bit field of that entry (`+0x42`). The damage handler branches on it: **1** and **2** are the two cases it handles; any other value skips the pools (`0x188e50`).
- With state **1** the damage counter is *not* added to the boss's hit points. It is taken off a pool: the ice pool (`+0xa8`) while the ice is up (`+0x9f` = 0), otherwise the armor pool (`+0xac`, set to the boss's own `+0x34` value / 20 at init). With state **2** the damage is added to a running total (`+0xb8`) that lowers the boss's hit points (`+0x34 = min(+0x34, +0x38 - +0xb8)`), and a 19200-tick timer (`+0xbc`) is set; the ice regrowth block only runs while `+0xbc` is 0.
- So the ice is the **first layer of a shield**, not a lock: once fire has worn the ice pool below the constant at 0x2b126c the hits go to the armor pool instead, and when that is empty the phase change happens (regrowth stops, 1920-tick timer, then animations 2, 3 and 0x18 are triggered). Whether real hit-point damage only lands after that change (state 2) is the natural reading, but what state codes 1 and 2 mean for BOS07's poses was not decoded.
- This fits the in-game observation that removing the ice does little to stop the ship by itself.
- **Endurance (from the game's own superweapon viewer, screenshots 2026-11-15): Habakkuk 80,000, speed 20 kts.** The boss's own `+0x34` / `+0x38` pair is very probably this value, so the armor pool (`+0xac` = `+0x34` / 20) would start at **4,000** and the ice pieces (100,000 each) are bigger than the whole ship's endurance. Inferred from the numbers, not read from a table. The viewer's weapon list for Habakkuk: 56.0cm Gun, Particle Gun, 127mm Gatling Cannon, 46.0cm Gun, X-ray Ordnance, Particle Gun (data/boss_viewer.json).
