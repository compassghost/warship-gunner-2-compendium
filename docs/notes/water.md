# Water: what the game files say, and the smooth water generator

## Decoded (2026-11-15)
- `MAP.BIN` opens with **five groups of three entries** (see `tools/export_water.py`, `tools/export_water_set.py`): entry 3g = a 16,384-byte block, entries 3g+1 and 3g+2 = two 8-bit indexed `SHTXFS` sea tiles (128 x 128; the last group's first tile is 128 x 64), each with its own 256-colour palette.
- The 16 KB block is **16 alternate 256-colour palettes** (1,024 bytes each, B G R A like every palette in the game, 4,096 colours in all). Applying them to the tile's index image gives 16 recolours: blue-grey, dusk brown, night dark and so on. So the game recolours the sea by palette (time of day / weather); it does not store one picture per variant. Tile A (entries 1, 4, 7, 10, 13) is the rough highlight layer, tile B (2, 5, 8, 11, 14) the softer base.
- The map table (DAT entry 4, 40-byte records, see `tools/extract_minimaps.py`) ends in two floats (1.0 / 1.0 on open sea, 0.6-0.9 elsewhere: fog / water strength?) and a flag word whose low byte (0, 4, 5, 6, 7, 8 ...) may choose the palette; **which palette or group a mission uses was not decoded**, and neither was how the game moves the tiles (scrolling, blending, wave mesh). I did not find the sea drawing code in the executable.

## The generator (`web/water.js`, demo `web/water.html`)
- A THREE.js ShaderMaterial on a large grid. The shader does the palette lookup itself and filters the colours **after** the lookup (bilinear on the indices' colours), so there is no banding or blocky pixels. Three scaled / rotated / drifting copies of tile B are mixed with a slowly moving weight so no repeat shows, tile A adds highlights and a small bump normal, four sine waves move the surface and give the normal, plus sun glints, Fresnel sky tint, distance fog taken from the palette's brightest colours, and an edge fade.
- Options: tile group, palette (the tiles' own colours or one of the 16 alternates), tile size, wave height and length, speed, highlight layer, bump, sun height, smooth / pixel. `WGWater.load()` / `WGWater.create()` is the API (header of the file).
- **The motion is my choice**, not the game's. Colours and tile contents are the game's.
- Used by `web/water.html` (controls), `web/drydock.html`, and the Water option of `web/models.html` (ships, bosses, composites; falls back to the old tile plane if it cannot load). Data: `web/water/` (index images, palette strips, `water.json`).

## Palette choice and weather (decode attempt, 2026-11-16)
- **Map record field (DAT 4, u16 at +36, "r18")**: low byte is 15, 5 or 10 and the high byte 0, 1 or 2 (values 15, 271 = 0x10f, 527 = 0x20f, 261 = 0x105, 5, 517 = 0x205, 10). Hypothesis (not confirmed): low byte = the map's default sea palette row, high byte = the tile group. Evidence: the 16 palette rows of every group are two sets of eight with the same colour sequence (rows 0-7 and 8-15: blue-grey day, warm, orange, dark red, night blue, bright warm, bright grey, grey-blue), and the three default values 15, 5 and 10 land on a grey-blue day row, a bright warm row and an orange dusk row, i.e. three of the four time-of-day options of the mission briefing (Dusk / Noon / Dawn / Night, DAT 18). The dock records (67-73) have 15 (high byte 0), so the dock viewer now uses group 0 row 15, which looks like the in-game dock sea (grey-blue sea, grey sky).
- The field after it (u16 at +38, "r19") is a flag word (0, 4-8 low bits, 0x400 for the docks, 0x2000 for some maps); its meaning is unknown. The two floats at +28 / +32 (1.0 / 1.0 on open sea and docks, 0.6-0.93 on other maps) are probably fog or water strength, unconfirmed.
- **Fog and weather exist in the game**: the executable has a weather system (debug strings `bad weather_v.`, `bad nex_weather_v.`, `bad2 weather_v. %d %d`, `no weather data`, `free_misson weather table err`). The update function around 0x147de0 reads a weather value 0-12 (byte at 0x2b27c2; previous one at 0x2b27c3, anything above 12 is an error) and cross-fades between two weather parameter sets (built by 0x148b78 from time-keyed tables, entries 0x1c / 0x24 bytes) with a blend factor, interpolating four colours (0x1461e8 is the colour blend) and floats: very likely sky / fog colours and distances. The tables are mission data parsed by the routine at 0x137a00-0x137d40 (entries of 0xd8 bytes with a 13-byte run per entry: probably one byte per weather value). Not decoded further: which archive holds them, the exact fields, how weather value maps to palette rows.
- The viewer's fog is my invention (the mean of the brightest palette colours); the game's is these interpolated colours / distances.
- **Day cycle reading (inferred)**: each group's 16 palette rows are two runs of eight in the same colour order (blue-grey, warm, orange, dark red, night blue, bright warm, bright grey, grey-blue), which looks like a day cycle (day, afternoon, dusk, late dusk, night, then dawn / overcast / day again). The mission briefing offers Dusk / Noon / Dawn / Night and the map records' default rows are 15, 5, 10. The dock page now has a Time selector: Noon = row 15 (the dock record's value), Dusk = row 10, Night = row 12, Dawn = row 5; Dusk and Night switch the lights on (lamp glow, beams, flare cards) and dim the dock and props (x0.75 / x0.4; Dawn x0.9). The row choices for Dusk / Night / Dawn and the dimming factors are my choices, not game values.
- The weather tables themselves (13 weather values, colours cross-faded by time) were not located: the parser at 0x137a00-0x137d40 reads them from stage data whose source archive I did not identify; the mission script header counts (BEV 206-281 record kinds 3 / 4) are not weather values (they range 1-23).
