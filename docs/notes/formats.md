# Warship Gunner 2 (USA, SLUS-21387) - format notes

Findings so far, in the order they were established. "Confirmed" means checked against the data; "Hypothesis" means not yet proven.

## Disc layout (confirmed)
Plain ISO9660 extracts with 7-Zip. `DUMMY1`/`DUMMY2` are padding. Game data lives in `*.BIN` / `*.BLN` archives, per-mission `DBGM/*.W` and `DBG2/*.W`, and `MV/*.PSS` movies. The main ELF is `SLUS_213.87` (load address 0x100000 = file offset 0x1000).

## Archive container (`*.BIN`) (confirmed)
Header, little-endian u32 x4: `count, base (0x800), unit, shift`. Then `count + 1` u32 words.
- `word[0]` is the size mask (e.g. 0x1FFFF for shift 17).
- For file `j` (1..count): `offset = (word[j] >> shift) * base`, `size = (word[j] & mask) * unit`.
- Derived from the game's own lookup routine at 0x101118 and validated: no entry runs past end-of-file in any of BEV, CHR, DAT, DSN, EFC, EVT, MAP, MDT_SHIP, MDT_WEPH, MDT_WEPL, PRV, and the summed sizes are within a few percent of the file sizes.
- Entry counts: DAT 41, DSN 231, MDT_SHIP 580, MDT_WEPH 790, MDT_WEPL 790, CHR 1827, MAP 811, EVT 423, BEV 359, PRV 14, EFC 3.

## Entry contents (partly understood)
Entries are not raw files. Each starts with a type-like byte followed by an ASCII tag, for example `0c 'SHT' 'X' ...`, `0d 'PSC'`, `07 'PTC'`, `'WL01'`. Some entries have a two-byte prefix (`24 0c 'SH'`).
- `SHTX` is checked by the executable's texture-upload code at 0x229d98 (it copies a 0x400-byte block, i.e. a 256-entry palette, then pixel data to the GS), so `SHTX` entries are very likely the game's images (candidate source for the flags).
- The bytes after the tag are not a plain palette/bitmap: they look like a custom compressed or delta-coded stream. The entry-level compression is NOT yet decoded.
- DAT.BIN entries contain readable hull names such as "Jpn Destroyer" and "German Submarine U-513" (the dash is Shift-JIS 0x815D), inside a compact record structure. Probably tech-tree layout data. Not yet decoded.

## Saves (confirmed)
`.cbs` (CodeBreaker) files unpack with `tools/unpack_cbs.py`. Three 39,964-byte slots per save, not encrypted, first 8 bytes of each slot differ between the two saves (probably a checksum).

## Entry compression (confirmed)
Every entry is compressed with a small LZ variant. The game's routine is at 0x22E640 (`tools/wg2.py: decompress`). Token byte `c`:
`00` end; `01-1F` literal run; `20-3F` literal run with 13-bit length; `40-4F` / `50-5F` byte fill (length 4+); `60-7F` continue the previous back-reference; `80-FF` back-reference, length `c>>5` (4-7), distance 13 bits. Decodes every entry of BEV, DAT, EFC, EVT, MDT_SHIP, MDT_WEPH, MDT_WEPL, PRV without error. Some CHR/MAP/DSN entries are flagged by my length check but are padding differences or other formats, not checked yet.

## SHTX images (confirmed)
Decompressed layout: `"SHTXFS"`, 6 header bytes (`[10]`,`[11]` = log2 width, log2 height), 256-entry palette stored B,G,R,A in plain linear order (a smooth brightness ramp in file order), then width x height linear 8-bit indices. Alpha is a full 0-255 range. 3,272 such images exist across the archives (CHR 983, MAP 624, EVT 396, MDT_WEPH 395, MDT_WEPL 395, MDT_SHIP 290, DSN 177). Some other variants (not 8bpp/linear, e.g. the ship pictures in DSN 133-152 render striped) are not decoded yet.
- `DSN.BIN`: medals, UI sheets, ship pictures, world maps, "CONFIDENTIAL" cards.
- `CHR.BIN` 1762-1826: **flags**, 64x64. 1762-1793 are named (32 names), 1794-1819 are 26 unnamed flags that are the international signal-flag alphabet A-Z, 1820-1826 are blank. The flag art sits in the top ~34 rows.

## English text (partly understood)
`DAT.BIN` entry 14 (30,968 bytes) is a string table with an offset table at the start. Contains flag names (in the same order as the images) and, nearby, hull and weapon names. Likely the source of English names for the tech tree. DAT entries 3, 33 and 34 also hold hull names (some with Japanese Shift-JIS alternatives).

## DAT.BIN layout (confirmed structure, most fields not yet decoded)
All 41 entries decompress with `wg2.decompress`. 33 of them share a generic table layout (`tools/dat_tables.py`): `u32 n, u32 total, u32 start`, then `n` pairs `(offset, count)`; each pair is an array of `count` fixed-size records (size = distance to next offset / count).
- **String tables** (every count = 1, Shift-JIS/ASCII, `#u85`-style colour codes): entry 13 (game messages), 14 (1,179 names: menu headings, caliber/size fragments, weapon and structure names, hull names, system names; the tech-tree labels are assembled from these fragments, e.g. "Gun " + "45Cal"), 15 (1,650 UI strings), 16-25 (menu/dialog text, staff credits), 29, 33 and 34 (weapon/structure naming rules and variants), 35/37/39/40 (tutorial text).
- **Record tables** (not yet decoded): entry 3 (1,023 x 24-byte part records plus a 1,072-record table referencing model files like `PREVC.BNC`), entry 6 (259 x 132 B, 73 x 20 B, 41 x 128 B, 300 x 180 B: the 132/180-byte records repeat 44/60-byte sub-records, probably three levels per item), entry 1 (721 x 12 B), entry 0, entry 2 (31 small arrays), entry 5 (449 x 12 B plus a 395 KB blob), entry 28.
- Not in the generic layout: entries 7-11, 26/27/36 (hull/design name lists starting with a length byte then text such as "Japanese Battleship"), 31, 32, 38.
- Hull names found (entry 14): Destroyer, Cruiser, Battleship, Carrier, Battlecarrier, Submarine, Frigate, plus special hulls (Small/Twin-hull Destroyer, Mini Destroyer, Special Cruiser, Drillship, Duckship, Supercarrier, Shark Submarine, Gigantic Battlecarrier, etc.).

## Guide data (tools/parse_guides.py -> data/guide_items.json)
Parses the five GameFAQs guides (kept in the project root, not redistributed) into 1,083 items: hulls 145, structures 214 (120 forward bridges, 82 aft bridges, 12 other), engine parts 97 (13 boilers, 13 gas turbines, 22 reactors, 26 propulsion, 23 smokestacks), armour 17, weapons 219 (base variants only), systems 141, aircraft 250.
Known gaps versus the game: the game's R&D screen shows 181 hulls but the ship guide lists 145 (the rest are probably Secret Blueprint hulls, which the guide omits); the weapons guide lists only the smallest variant of each gun (the game has 518 gun variants from 7 cal-lengths x 4 barrel counts) and has no 80.0cm main gun although the rewards guide mentions one; research requirements are not in any guide. Three aircraft names appear twice (Walrus, Altr II, Ju88A); not yet checked whether those are real duplicates.

## Tech tree data (what is known, prompt 16; edges NOT decoded yet)
**Chip names.** `DAT.BIN` entry 33 (decompressed, string-table layout) is the master list of tree chip labels: entries 0-1005 are chip names in tree order (guns by diameter / cal-length / barrels, then ammo, hi-angle, machine guns, rapid-fire, proto, torpedoes, explosives, missiles, rockets, flares, organic, optical, plasma, magnetic, pulse, then HULLS, BRIDGE, AFT, FACILITY, POWER, ROTATION, ATTACK/DEFENSE/STEERING SYSTEMS, ENIGMA, then aircraft). Entries 1006-1039 are the 34 lane/group headings: MAIN, AMMO, HI ANGLE, MACHINE, RAPID, PROTO, TORPEDO, EXPLOSIVE, MISSILE, ROCKET, FLARE, ORGANIC, OPTICAL, PLASMA, MAGNETIC, PULSE, A-MATTER, HULLS, BRIDGE, AFT, FACILITY, POWER, ROTATION, PURGE, ATTACK, DEFENSE, STEERING, ENIGMA, FIGHTER, INTERCEPT, BOMBER, SCOUT, HELI, SPECIAL. Entry 34 is the same list with Japanese text interleaved.
**R&D rules (from the game's own tutorial text, entries 39/40).** Trees start at the upper left and get more advanced downwards; a chip cannot be developed unless the chip before it in the tree is at least under development; branches merge when several parts are prerequisites; some chips are hidden (dotted line) until conditions are met; locked chips show conditions such as "Required part is not ready / not available", "Required medal not received", "Required stage not cleared"; status text is AVAILABLE, RESEARCHING, READY or REQUIRED; items have TURNS and COST. Guns are built from diameter x length (cal) x barrel count; developing a cal/barrel branch enables it for every directly connected diameter; hulls are level chips (Destroyer I..) with country chips (Jpn, U.S., U.K., Ger) per level; bridges and boilers work the same way.
**Layout table (entry 0).** arr 4 (241 x 14 bytes): `u16 0x2400, u16 ?, u16 chip id (7002-7264), u16 turns?, ...` plus arr 5 (241 x 4 bytes): `byte y(0-80), byte lane x(0-4), u16 style`. Five vertical lanes of up to 81 rows. Probably one category's tree (the aircraft tree is the best guess: 241 chips vs 259 aircraft records in entry 6). Unverified.
**Stat tables found by value-matching against the guides.** Entry 6 arr 0 (259 x 132 B, three 44-byte sub-records) holds aircraft speed/endurance (258 of 259 rows match guide values); entry 6 arr 3 (300 x 180 B, three 60-byte sub-records) holds weapon damage/range. Hull stats from the ship guide were not found as plain 16/32-bit or float values anywhere in the archives or the executable, so hull stats are stored in another form.
**Condition lists (candidates for prerequisites).** Entry 3 arr 1 is a list of zero-terminated u16 sequences, each starting with a chip number followed by condition codes (e.g. `594, 57, 20040, 20059, 20060, 79, 0`). Entry 28 has 84 nodes with `(value, type)` pairs (type 0, 1, 3, 4, 5, 6, 9) that look like part / stage / medal conditions. Neither is decoded yet.

## In-game tree ground truth (from user screenshots, prompt 18)
Tree = 34 separate lanes/groups, each with its own chip count in the complete save: MAIN 103, AMMO 6, HI ANGLE 8, MACHINE 17, RAPID 10, PROTO 16, TORPEDO 118, EXPLOSIVE 11, MISSILE 41, ROCKET 12, FLARE 4, ORGANIC 5, OPTICAL 24, PLASMA 15, MAGNETIC 5, PULSE 6, A-MATTER 1, HULLS 181, BRIDGE 160, AFT 109, FACILITY 7, POWER 105, ROTATION 31, PURGE 9, ATTACK 74, DEFENSE 41, STEERING 9, ENIGMA 8, FIGHTER 49 (INTERCEPT, BOMBER, SCOUT, HELI, SPECIAL not yet photographed). These 29 sum to 1,180; with the five aircraft trees still to be counted the total should be about 1,500.
Chips are not the same as names: the chip-name list (entry 33) holds each distinct label once ("50Cal" appears once but is a chip in every diameter row).
Layout rules seen in MAIN: a trunk runs down the left through the diameter chips (10.0cm, 12.7cm, 14.0cm, ...); each diameter has a horizontal chain of cal-length chips (50Cal, 55Cal, 60Cal, 65Cal, ...); barrel-count chips (2 brls, 3 brls, 4 brls) hang off a vertical bus that is attached to the diameter's row, in a row below. Hidden chips are drawn with a dotted line. A fresh/early save (1450 items) shows MAIN 1/65: only 65 of the 103 chips are visible until prerequisites are met. Chip colours: grey done, yellow researching, green available, blue lacks funds, red slash locked (e.g. 65Cal, 3 brls). FIGHTER tree: columns of aircraft chained top to bottom (M6A1 > M6A2 > G4M-1 > G3M-96 > B5N-97; Devast > TBF-1 > AD1 > A-4P > Yak-38; Swfish > Alba > Brrc I ...) with short side branches (TBF-1 > TBF-3). Aircraft chips use abbreviated names (probably DAT entry 29).
Global file ids in the executable: id = archive base + entry; DAT is 6000 + entry (MAP 0, CHR 2000, EFC 4000, PRV 5000, DAT 6000, SNDPS2 7000, BEV 8000, DSN 11000, EVT 15000, MDT_SHIP 18000, MDT_WEPH 19000, MDT_WEPL 21000, VCEPS2J 24000). DAT entries 1-11, 14, 15, 22, 23, 28, 31 are loaded together at startup (code at 0x103BA0), entry 0 is used by code around 0x146000-0x14A000.
Not found: the per-tree chip layout/edges for the other 33 groups. Entry 0 (241 chips) is the only table with that record type, so the rest are stored differently; the group sizes do not appear as a count table anywhere searched.

## TECH TREE DECODED (prompt 19) - supersedes the earlier tree notes
**Numbering correction.** The game's DAT ids are shifted by one from this project's entry numbers: the game computes `entry = id - 6000` but reads the archive word at index `entry`, and word 0 is the size mask, so game entry k = project entry k-1 (game id 6032 = project entry 31). Global file id = archive base + entry: MAP 0, CHR 2000, EFC 4000, PRV 5000, DAT 6000, SNDPS2 7000, BEV 8000, DSN 11000, EVT 15000, MDT_SHIP 18000, MDT_WEPH 19000, MDT_WEPL 21000, VCEPS2J 24000 (tables at 0x2A6B90 and 0x28B638 in the executable). Earlier notes that treated project entry 0 as a tree layout were wrong: it is sound-effect configuration (ids 7002+ are SNDPS2 entries).
**R&D master table = project entry 31** (304,680 bytes; loaded by the R&D screen at 0x203130; code `tools/decode_rd_tree.py`). Layout: `u16 sizes[34]` (chips per group incl. root), `u32 T48[34]@0x48` (per group: array of 64-byte chip records), `u32 T114[34]@0x114` (per group: rows of up to 16 chip indices in drawing order), `u32 T19c[34]@0x19c` (per group: 128-byte lists of ALL chips that must be developed first, -1 terminated). Global chip number = sum of earlier group sizes + index in group (game helper at 0x213F78); the game keeps per-chip state bytes for 1,500 chips.
**64-byte chip record (i16 fields):** [3] item id, [4] kind (low byte 1 level/diameter, 2 normal, 3 branch; +0x100 = hidden until unlocked), [5] turns, [6] cost, [8] label index into project entry 34 (the game's English/Japanese label table), [16] condition flag bits (16/32/64/128/...), [17]-[20] condition parameters (-1 = none), [22] column x, [23] row y (999 = not placed on the tree), [24..31] drawn neighbours (first = parent). Direct prerequisites = transitive reduction of the T19c ancestor list.
**Validation.** For all 29 groups photographed in-game, the number of placed chips equals the in-game ITEMS count exactly (MAIN 103, TORPEDO 118, HULLS 181, BRIDGE 160, AFT 109, POWER 105, ATTACK 74, FIGHTER 49, ...). MAIN costs/turns match screenshots (50Cal 100:1, 55Cal 150:1, 12.7cm 600:2, 2 brls 200:1, 3 brls 300:1); the drawn layout and the FIGHTER chains (M6A1 > M6A2 > G4M-1 > G3M-96 > B5N-97; Devast > TBF-1 > AD1/TBF-3 > A-4P ...) match. In the 1450-item save the two red-slashed MAIN chips (65Cal = MAIN 5, 3 brls = MAIN 9) are exactly the ones with non-zero condition fields.
**Totals.** 1,409 chips in 34 groups including 34 roots; 1,375 placed. The tutorial says 1,500 state slots; the difference is unplaced chips (50) and pickup-only items.
**Not decoded yet:** the meaning of the condition bits and parameters (stage / medal / recovered part conditions), the hidden-chip unlock rules, and the mapping from chips to full item names and stats (field [3] is an item id; hull chips are level + country pairs such as DD I > Jpn).

## Unlock conditions (prompt 20)
The R&D screen's condition evaluator is at 0x214EA0 in the executable. For a chip record `rec` (64 bytes) the *byte* at 0x20 (low byte of i16 field 16) is a bit mask; each set bit adds one check:
- 0x20: chip (group = field 18, chip = field 19) must be READY. Cross-group references are common (e.g. 17 hull chips require HULLS 80). Text: "Required part is not ready."
- 0x10: medal/flag index = field 17 (byte) must have been received. The 84-byte status table lives at save offset 0x76 (bits &7 = received). Index 0-15 = Silver Swan classes, 16-55 = service medals/ribbons, 56+ = flags, in the order of DAT entry 14 strings 995-1082. Text: "Required medal not received."
- 0x40: story progress byte (save offset 0x4B0; 15 in both complete saves) must be >= field 20. Text: "Required stage not cleared."
- 0x80: the matching part/plan must have been recovered from the enemy (evaluated by per-group helpers at 0x10A568 / 0x10A6C0 / 0x10A7D0 / 0x10A8E0).
- 0x08: a global counter at 0x2B2819 must be >= (field 16 >> 8). Which counter this is has not been identified.
- 0x01/0x02/0x04: captain route gate. Each bit blocks route 0/1/2 respectively (save offset 0x1A2); e.g. HULLS 26 (Jpn) = bits 2+4 so route 0 only, HULLS 29 (Ger) = route 1 only, HULLS 28 (U.K.) = route 2 only. Route numbers are not yet matched to Tsukuba / Werner / Braun (nationality suggests 0 = Tsukuba, 1 = Werner, 2 = Braun, unconfirmed).
Counts over all chips: medal/flag 259, story progress 180, other chip 118, recovered part 94, counter 33, route 13.
Check against the in-game 1450-item screenshot: MAIN 65Cal (needs 20.3cm) and MAIN 3 brls (needs 20.3cm and progress >= 2) are the red-slashed chips; 60Cal, 2 brls, 50Cal and 55Cal, which have no conditions, are not.
Save files: in BASLUS-21387WG2xx slots the struct starts at offset 0 (medal table at 0x76). The 12082 save has bit 0x40 set on all medal/flag entries and the 11756 save does not, so 12082 is the 1500/1500 save and 11756 the 1494/1500 one (inferred from the data, not from the upload names).

## Tree corrections (prompt 21)
- Chip cost is a 32-bit value: field [6] (low 16 bits, unsigned) | field [7] << 16. The earlier signed 16-bit read produced negative costs (e.g. AMMO ARM -11072; correct 120,000). AMMO costs: T Fuse 5,000, P Fuse 25,000, PRC 50,000, N PRC 80,000, ARM 120,000, N ARM 200,000; the largest cost in the tree is 900,000 (HULLS "BB x2").
- Line routing in the game's tree screen (inferred from the AMMO and MAIN screenshots): same row/column = straight line; if the parent already has a child to its right in its own row, other branches hang off that horizontal line through a vertical bus beside the parent (MAIN barrels); otherwise a branch leaves the parent's bottom, runs along a bus midway to the next row and drops into the child's top (AMMO). Chips with two parents (PRC, N PRC) get one line per parent.
- AMMO check: chip ancestors give PRC <- T Fuse + ARM, N PRC <- P Fuse + PRC, P Fuse <- T Fuse, N ARM <- ARM, which is exactly what the in-game drawing shows.
## Item link groundwork
Field [3] of a chip record is an item/part id in one global numbering (0..972): guns 0-232 in the artillery/launcher groups, hulls from 233, bridges/boilers/systems 285-539, aircraft 553-966; level chips (DD I etc.) reuse shared ids (234-239). Ids above 900 are special/pickup variants. DAT entry 3 array 2 (1,023 x 24-byte records) looks like an item -> model table: u16 pairs such as (3637, 3636) are global file ids (CHR.BIN entries). ## Full item names (prompt 22) - tools/full_names.py
- Project DAT entry 33 is the game's full-name fragment table: indices 0-33 are one generic fragment per group (" Gun", "", " High Angle Gun", ...), index 34+ are the item/chip fragments in tree order ("MAIN", "10.0cm", " 50Cal", ..., "Destroyer Ⅰ", "Jpn ", "Boiler Ⅰ", "DD Steam Turbine Ⅰ", ...).
- A chip's fragment is `S33[item_id + 34]` (chip field [3] + 34). Chip field [14] indexes a template string in entry 34. Template tokens (only these four exist): `~Ca1` this chip's fragment, `~Ca0` the group's generic fragment (`S33[group]`), `~Ip` the parent chip's fragment, `~Iw` the fragment of the nearest ancestor of kind 1 (diameter / level chip). A template with no tokens is an explicit full name. Default template is `~Ca1`.
- Examples produced: "12.7cm Gun 45Cal" (matches the in-game detail title), "10.0cm Gun 50Cal", "Jpn Destroyer Ⅰ", "U.S. Battleship Ⅳ", "CV Boiler Ⅰ", "Jpn DD FWD Bridge Ⅰ", "New Armor-Piercing", "M6A1 Seiran".
- Check against the guides: 144 of 145 guide hull names, 208 of 214 structures, 134 of 141 systems and 190 of 219 weapons (the rest differ only in wording, e.g. the guide omits the cal-length) appear in the game-derived names. The one missing hull, "U.K. Destroyer 6", is the hull the ship guide says cannot be researched. Aircraft chip labels are the guide's abbreviations (A-4P) while the full names are longer ("A-4P SkyHawk").
- 10 chips have no composable name (BRIDGE 144-146, AFT 25, FACILITY 8-9, INTERCEPT 89, BOMBER 13-14, HELI 9); the viewer falls back to their short label.

## Item stats: aircraft (prompt 23) - tools/item_stats.py
Aircraft records: project DAT entry 6 array 0, 259 records x 132 bytes = 3 x 44-byte sub-records (three strength levels; the middle one equals the guides' values). Record r belongs to the chip given by pairs[r+1] of project entry 32 (u16 pairs, (group, chip index); the +1 is the same index shift as the archive numbering). Sub-record u16 fields: [2] range, [4] endurance, [5] speed, [9]>>8 gear (0 wheels, 1 floats, 2 VTOL, 3 helicopter), [10] bit0 night-capable and bit8 heavy-weather-capable, [15]/[16] weapon ids (9000+), [18]/[19] rounds for those weapons. 250 aircraft chips have stats; 183 of 191 checkable aircraft match the guide exactly, and A-4P SkyHawk matches the in-game screen (speed 1080, range 285, endurance 85, night and heavy weather OK, 30mm MG x40, 100lb bomb x4). Weapon ids were named by matching loadouts against the guide (24 ids); the game's own weapon-id table is not located yet.
Not yet found: weapon stats (damage/reload/range, entry 6 array 3 is the likely source), hull, structure, engine and system stats (not stored as plain 16/32-bit numbers in any decoded table).

## Line routing check (prompt 27)
The tree page tests every candidate route against all chip rectangles (a line must not cross a chip that is not one of its two ends) and uses the first clean one: the game-style rule decides the preferred order (horizontal-first when the parent already has a child in its row, vertical-first otherwise), and the other routes, plus a "bus next to the child" route, are fallbacks. Before the fix 19 edges ran through other chips in Standard and Compact modes (TORPEDO 3 incl. AST, MISSILE 1, ROCKET 1, HULLS 8, BRIDGE 3, AFT 2, INTERCEPT 1) and 4 in Collapsed (TORPEDO, MISSILE, ROCKET, INTERCEPT); after the fix 0 of 1,392 edges (Standard/Compact) and 0 of 832 (Collapsed) are blocked. The page keeps these numbers in `window.__edgeStats` after every render, so the check can be re-run in the browser console.

## PSC1 models and the viewer (prompt 61)
- `tools/psc1.py` documents the container: header block size at 0x38, part slot table at 0x40, per part a vertex block (10-byte records, s16 x y z), a face block (24-byte records starting with three u16 indices), plus UV/colour/normal tables not decoded. Textures (`SHTX` / `SHTXST`) are not mapped onto models yet.
- CHR.BIN has about 680 PSC1 models: ships (for example 1230-1306), superweapons (1216, 1185, ...), aircraft (for example 171, 177, 905, 1019, 1034) and small parts. A model is usually followed by its texture entry.
- The item-to-model table (DAT entry 3 array 2) is not reliable: the duck items point at ship models, and an aircraft item pointed at an octagonal-prism part. Models are therefore browsed by entry number.
- `tools/export_models.py` writes `web/models/*.bin` (747 models of 300+ vertices, 13 MB) and `web/models.html` shows them with three.js (rotate by dragging, wheel to zoom, up-axis and wireframe buttons). Some triangles are missing or ragged, so the face block is probably not complete (strip or flag records).
- Face records are quads: four u16 indices in outline order (a, b, c, e), a triangle when e == c, otherwise split as (a,b,c) + (a,c,e). Every quad in three test models was convex in that order. Reading only three indices had dropped the second triangle of each quad (the "missing faces").
- Aircraft models: chr_689 (user-identified F-15-like jet) has part 0 as the high-detail mesh and part 1 as a low-poly variant. Its texture is the `SHTXST` entry just before it (688, 66,568 bytes = 256x256 8-bit plus palette), which looks like a PS2-swizzled variant of SHTX; the `SHTXFS` kind is the plain linear one already decoded. Ship models have up to four parts (0 and 1 are detail levels, 4 differs).
- `web/models/names.json` ({"chr_689": "F-15-like jet"}) holds hand-written names shown in the viewer list and info bar.
- Known viewer defects (prompt 65): on chr_1100 (a helicopter) the rotor disk sits under the airframe, and some ship bridges are misplaced. Sub-objects such as rotors and bridges probably carry their own offsets in the header block (before B): chr_1100 has records of float values at 0x3a4-0x400 and an object name string (`..HE_03`) at 0x3fc, which have not been decoded. Vertex tags (the last u16 of a vertex record) are per-vertex ids, not object numbers.
- Texture coordinates (prompt 66): per-face 20-byte records at part word [9]: four (u, v) u16 pairs (divide by 16384) plus a 4-byte header. `SHTXST` textures are 8-bit linear with an 8-byte header ('SHTXST' + 2 bytes, 1024-byte palette, then pixels; 256x256 for the aircraft). The texture of a model is the SHTX entry directly before it (chr_689 uses 688; the afterburner nozzle UVs land on the flame sprites in the texture's bottom row). The UV records match the faces for about the first half of a model and then show stray zero pairs.
- `web/models/` now holds .bin and .png per model (113 MB); keep it out of any published copy of the site.
- UV records vs faces (prompt 68): a model can have fewer UV records than faces (chr_689: 618 records for 632 faces; the faces on the mirrored half were previously shifted). `psc1.align` matches faces to records in order with a banded dynamic programme, letting a few faces go without a record (they get zero UVs). With it both halves of chr_689 are textured correctly.
- Holes: faces never have invalid indices (checked on 86,000 faces); the viewer now splits non-convex quads along the diagonal whose triangles face the same way. Any remaining holes are probably faces that sit in other parts or tables that are not decoded.
- Large models (chr_1158, chr_1160 and other superweapons / carriers) store vertices as 16-byte records (u16 0, u16 id, s32 x, s32 y, s32 z) instead of 4-byte prefix + 10-byte s16 records; the choice is the vertex block size divided by the vertex count. Read as s16 they looked like malformed star shapes. The exported .bin now holds Float32 vertices. `psc1.align` was rewritten as an O(faces x skips) dynamic programme (the first version took minutes on large models).
- Big models have far fewer UV records than faces (chr_1198: 939 records for 2242 faces; chr_1216: 2787 for 5618; chr_1672: 2078 for 2897) and the records are not in face order (chr_1198: the first 80 faces are all quads while the records contain triangles from the 26th). The face-to-record link is therefore unknown for these models; the in-order alignment (`psc1.align`) is only reliable when nearly every face has a record (aircraft). Leads: the 16-bit field at vertex offset 6 holds 64 / 192 in chr_1198 (0 in chr_689), and the last two u16 of a UV record are (0, 0x407f / 0x7f); neither is understood. Face record bytes 12-15 look like a float, not a material id.
- The viewer's near plane is now scaled to the model (z-fighting) and untextured faces are light grey.

## PSC1 decoded: model audit (2026-11-12) - supersedes the PSC1 notes above where they differ
Full write-up: `notes/model_audit.md`; lists: `notes/model_entities.md`, `notes/model_placement.md`; layout reference: the docstring of `tools/psc1.py`.
- **Face -> UV link (solved).** UV records are shared between faces. The u16 at face offset 14 is the index of the face's UV record; bit 15 set or 0xffff means the face has no texture. `psc1.align` (in-order matching) is gone. The u16 at face offset 22 is a normal index, offset 10 a colour-table index, offset 12 a material value (0xbf00 in most faces).
- **Nodes (solved).** Header: u8 [4] node count, u16 [0x0a] animation frames, [0x0c] position entries, [0x0e] rotation entries, u32 [0x20] position table (s16 x, y, z, u16 scale 1024 = 1), [0x24] rotation table (s16 x 3, 65536 = 360 degrees), [0x1c] hierarchy lists, [0x3c] model name. Each part has a 20-byte record per node at part + 0x40: vertex range, face range, radius, parent, child-list pointer, animation-track pointer ((position, rotation) index pair per frame). Vertices are node-local; world = parent chain, 1 position unit = 2 vertex units (8 with 32-bit vertices, header flag 8 at [8]). Frame 0 = rest pose.
- **Part slots.** Slot 0 full detail, 1-2 lower detail (part bytes [5..7] name the lower-detail slots, words [2..4] the switch distances), slot 4 an untextured collision hull.
- **Model resource table and entity class table (DAT entry 3).** Array 2 (24 bytes x 1,023): model file id, texture file id; the row number is the resource index. Array 3 is 1,072 records of **24** bytes (not 32): resource index, 7 u16 properties, u32, pointer to the entity name. This is the authoritative model -> texture and model -> name link (aircraft, enemy ships, superweapons, map objects). The earlier note that the item -> model table is "not reliable" came from indexing it with item ids; it is indexed by resource index.
- **Texture rule.** Use the table, not the neighbouring entry: 1,347 of 1,835 models had a different texture under the neighbour rule (all British and German enemy ships, all player hulls but one, dock objects, boss sub-models, effects).

## Music (LPCM), extracted 2026-11-13 - tools/extract_music.py
`DBGM/B01-B27.W` and `DBG2/B30-B47.W` (44 tracks, 68.6 minutes) are the background music, not mission data. Layout: 0x800-byte header = `'LPCM'`, u32 total sample frames, u32 loop start, u32 loop end (frame indices, end inclusive), rest zero; then raw interleaved signed 16-bit little-endian stereo (4 bytes per frame, frames x 4 bytes). Sample rate 48,000 Hz: B11 is exactly 5,280,000 frames (110.000 s) and the loop points fall on round seconds at that rate (B02 2.0-50.0 s, B10 30.0-162.0 s). Verified: every file reads back with the correct header, levels are normal for music, clipping is negligible. B45 and B46 are byte-identical. `tools/extract_music.py` writes `music/<folder>_<track>.wav` (753 MB) with the loop points stored as a WAV `smpl` chunk, and `data/music.json` (frames, seconds, loop points per track). Which track plays where (missions, menus, dock) is not mapped. Other audio not extracted: `SNDPS2.BIN` (sound effects), `VCEPS2J.BIN` (voices), `MV/*.PSS` (two movies).

### Music: how the game picks tracks (executable analysis, 2026-11-13; addresses are in-game, Capstone MIPS64 LE)
- A track number is simply the file number: numbers 1-29 load `\DBGM\B%02d.W`, 30-59 load `\DBG2\B%02d.W` (format strings at 0x2a68f0 / 0x2a6900). 0x100e40 is a start-up check that every name B00-B59 exists ("dbgm file no entry" otherwise); it does not play anything.
- **0x108fa8 is the play function** (`$a0` = track number, `$a1` = flag; 0 = stop via 0x109098). The whole program has only **11 call sites**: 0x108544, 0x108f9c (replay the current track), 0x109224 / 0x109294 / 0x1092d0 / 0x109344 (track numbers taken from two gp variables, see below), **0x136a94 (stage event: number = halfword at +8 of an event record)**, **0x15e4e0 (fixed track 20)**, 0x15e59c (variable), **0x19008c and 0x19055c (fixed track 4)**.
- 0x109120 reads a **table of 2-byte entries addressed backwards from a pointer** (`entry = base + 2*idx - 2` with a negative stage variable idx; byte 0 and byte 1 go to two gp variables, which the sites above then play). That is the most likely per-stage default music (two tracks per entry, e.g. normal / alternate), but where that table is stored (mission script, map file or elsewhere) was NOT found: it is not directly before the map object table in the MAP PSM0 files, and the BEV mission scripts' records were not decoded far enough (an attempt to parse them as op + 11 argument bytes + 4 payload bytes lost sync after the first text records).
- Not known: which screen the fixed calls (tracks 4 and 20) belong to, and the stage -> track assignment. No names exist in the game for any track.

### Music: stage music pairs (user-confirmed concept; table not found)
- Each stage has **two tracks: one out of combat, one in combat** (user, 2026-11-13). ### Music: stage music SOLVED (supersedes "table not found" above) - tools/build_stage_music.py -> data/stage_music.json, web/stage_music.json

### Music: mission-script records (BEV decoded, 2026-11-13)
- **BEV mission-script format solved** (parser `tools/bev_script.py`; BEV 204 and 206-281 parse exactly to the end of the entry; 205, 282-287 are tiny headers; 0-202 and 288-358 are per-unit AI scripts of another layout; 203 is a different table). File = `u32 nblocks`, then blocks `u16 A (type), u16 B (records), u16 0, u16 C, 2*C u16 (ids, values), pad4, B flag bytes, pad4, B records`; record = `u8 kind, u8 sub, 5 x u16 params, NUL-terminated string padded to 4`.
